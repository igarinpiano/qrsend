# 耐量子暗号への移行計画

QRSend の暗号を、量子計算機でも破れない形に移していく計画と、その進み具合。2026-10-12 開始。
仕様そのものは `PROTOCOL.md` §9.1 に書く。ここは「何を、どの順で、なぜ」の記録。

## なぜ必要か

QRSend のコードは画面に出る。画面は誰でも録画できるので、**いま録っておいて、将来量子計算機で解く** 攻撃が成り立つ。
これに弱いのは鍵の受け渡し（X25519）で、次が署名（Ed25519。こちらは攻撃の時点で量子計算機が要るので急ぎではないが、ユーザーの指示で同時に進める）。
本体の暗号（ChaCha20-Poly1305）とハッシュ（BLAKE3）はそのままでよい。

## 方針（決めたこと）

- **ハイブリッド**: 従来の方式を捨てず、耐量子の方式と **両方** を使う。片方が破れても、もう片方が残る（Apple の PQ3 と同じ考え方）。
  - 鍵の受け渡し: X25519 ＋ **ML-KEM-768**（FIPS 203）
  - 署名: Ed25519 ＋ **ML-DSA-65**（FIPS 204）
- **実装は自作しない**: RustCrypto の `ml-kem`（age が既に使っている版）と `ml-dsa`。どちらも純 Rust で、WASM でも動く（ユーザーの提案どおり ml-kem。署名はそれと同じ系統の ml-dsa にした）。
- **2 つの秘密の混ぜ方**: X-Wing（draft-connolly-cfrg-xwing-kem）の結合式 `SHA3-256(ss_ML-KEM ‖ ss_X25519 ‖ 使い捨ての X25519 公開鍵 ‖ 宛先の X25519 公開鍵 ‖ ラベル)`。ラベルは QRSend 専用（鍵の作り方が X-Wing と違うので、X-Wing そのものとは名乗らない）。
- **age の枠組みはそのまま**: age のヘッダに、QRSend 独自の種類のスタンザ（`qrsend-pq1`）を 1 つ足すだけ。本体の暗号化は age のまま。
- **宛先ごとに決める**: 相手のデバイス ID に耐量子の鍵があればハイブリッド、無ければ従来どおり。ハイブリッドの相手に従来のスタンザを **併せて付けることはしない**（付けると、そちらを解けば読めてしまう）。
- **署名は厳しく**: 耐量子の鍵を持つ送信者は **常に両方で署名** する。受信側は、相手の耐量子の鍵を知っているなら、両方の署名が正しいことを求める（片方だけなら拒否。「古い方式だけの署名」への格下げを許さない）。
  - 代償: 新しい署名の形式を古い版（0.1.10 以前）は読めない。耐量子の鍵を持つ送信者からの **署名つきの転送は、古い版では受け取れない**（「unsupported signature algorithm 2」）。受け取る側を更新する。
- **デバイス ID は版 2**: 公開鍵が 64 バイトから約 3.2 kB になる。1 個の QR には密すぎるので、**複数の QR に分けて順に表示する**（再生・一時停止・コマ送り。ユーザーの指示）。文字列の ID（`qrsend-id:2:…`、約 4,300 文字）はそのままコピーできる。
- **フィンガープリントは 20 桁**（版 2 の ID。従来は 12 桁 = 約 40 ビットで、もともと短かった）。
- 既存の ID はそのまま使える。更新すると耐量子の鍵が足され（従来の鍵は変わらない）、相手に **新しい ID を登録し直してもらった時点から** 耐量子になる。

## 大きさの目安

| もの | 従来 | 耐量子 |
|---|---|---|
| デバイス ID（公開鍵） | 64 B | 3,200 B（ML-KEM 1,184 ＋ ML-DSA 1,952 ＋ 従来 64） |
| ID の QR | 1 個 | 3 個（転送と同じ密度）〜 8 個（読みやすい密度） |
| 暗号化の上乗せ（宛先 1 つあたり） | 約 0.2 kB | 約 2.4 kB（ファイル一覧と本体で 1,088 B ずつ） |
| 署名 | 96 B | 3,405 B |
| 小さな暗号化転送（テキスト 1 行） | 約 0.9 kB | 約 6.5 kB |

## 記録

- 2026-10-12: 開始。フェーズ 0。
- 2026-10-12: フェーズ 1〜3（コアと CLI）。
  - ID の QR は **9 個前後**（QR バージョン 15・誤り訂正 M。端末に 81 桁 × 42 行で収まる大きさ）。転送と同じ密度（バージョン 25）なら 3 個で済むが、121 桁になり端末に収まりにくい。`qrsend id` は Enter で表示を始め、`space` で止める／再開、`←` `→` で 1 個ずつ。
  - 既存の鍵は、新しい版で初めて使ったときに耐量子の鍵が足される（従来の鍵はそのまま）。相手が持っている従来の ID の記録は、新しい ID を `devices add` し直すと **同じ記録に鍵が足される**。
  - `--secure` は、耐量子の鍵を持つ相手とだけやり取りする（従来の方式だけで暗号化されたものは開かない）。
  - （この時点の Web 版）コアを共有しているので、この時点で「版 2 の ID を文字列で登録する」「耐量子の相手にハイブリッドで暗号化して送る」「方式 2 の署名つきの転送を読む」はできる。自分の耐量子の鍵、ID を複数の QR で見せる／読むこと、ML-DSA の署名の検証は、フェーズ 4。
- 2026-10-12: フェーズ 4（Web）。
  - 鍵の保存: WebCrypto には ML-KEM / ML-DSA の鍵が無いので、**種（96 バイト）をそのまま IndexedDB に置く**（ページのスクリプトから読める）。ただし、復号にも署名にも従来の鍵（X25519 / Ed25519。WebCrypto の「取り出せない鍵」のまま）が **必ず一緒に要る** ので、種だけを盗んでも何も読めず、偽造もできない。AES の取り出せない鍵で包む案は、スクリプトがその鍵を「使う」ことはできてしまうので、得るものが小さいと判断して採らなかった。iPhone / Safari（鍵を文字列で持つ方式）は従来どおり全部が読める形。
  - 既存の ID は、ページを開いたときに耐量子の鍵が足される（CLI と同じ。従来の鍵はそのまま）。
  - Devices の画面: 自分の ID は 9 個ほどのコードが 0.7 秒ごとに切り替わる。◀ ▶ で 1 個ずつ、Hold / Go on で止める・再開。読む側（Scan）は「9 個中 5 個」と進み具合を出し、そろったらフィンガープリントの確認に進む。従来の ID で登録済みの相手は「older keys only」と表示され、新しい ID を登録すると同じ記録に鍵が足される。
  - e2e（`pq.spec.ts`）: ブラウザ → ブラウザ（カメラで、順番を崩して）、ブラウザ → CLI（画像）、CLI → ブラウザ（カメラ）で ID を読めること、記録の更新。既存の暗号化の e2e（CLI ⇄ Web）は、そのままハイブリッドで通っている。
- 2026-10-12: ユーザーの判断。
  - **署名は常に両方でよい**（「まだユーザーも少ないし、全員に耐量子を使ってほしい」）。古い版が読めなくなる点は受け入れる。
  - **従来の鍵は、廃止はしないが、使っていることが必ず見えるようにする**（「本当は古い鍵を廃止させたいが、非対応のデバイスが出てくるとややこしい」）。そのために:
    - 登録の画面は **2 種類の ID を出せる**（Web: Devices の「Show the ID for versions before post-quantum keys」、CLI: `qrsend id --classic`）。従来の ID を出している間は警告を出す。
    - デバイス一覧は、相手ごとに「post-quantum」か「older keys only」かを出し、従来の鍵だけの相手がいれば警告を出す（CLI の `devices list` も同じ）。
    - 送信側: 従来の鍵だけの相手を宛先に選ぶと警告（Web は選んだ時点、CLI は梱包の前）。送信中の表示にも「encrypted (post-quantum)」か「encrypted the older way only」を出す（CLI はウィンドウのタイトルと端末の状態行）。
    - 受信側: 「どう暗号化されていたか」（post-quantum / older encryption）と「署名をどう確かめたか」（post-quantum signature / older signature only）を出し、従来の方式なら警告を出す。受信が終わったあとの画面にも残す。
  - 「どう暗号化されていたか」は、age のヘッダのスタンザの種類から、鍵なしで判定する（`crypto::protection`）。宛先が複数あって 1 つでも従来のスタンザがあれば、**転送全体が従来の強さ**（ファイル鍵は全員共通なので）。
  - ライセンス: 新しい依存はすべて MIT / Apache-2.0 / BSD-3-Clause で、`deny.toml` の許可リストの範囲内、取得元は crates.io（`cargo metadata` で確認。`cargo deny` そのものは CI が実行する）。
- フェーズ 6 の検討（未着手のまま。理由を記録する）:
  - **直結の鍵を 256 ビットに**: 見送り。直結（TCP / WebRTC）を流れるのは、暗号化した転送なら既にハイブリッドで暗号化済みのデータで、直結の鍵が守るのは平文の転送と通信の管理だけ。128 ビットの共通鍵は量子計算機に対しても現実的に安全とされる水準（NIST のカテゴリ 1）で、形式を変えると版の違う CLI 同士がつながらなくなる。得るものが小さい。
  - **WebRTC の鍵交換**: ブラウザの DTLS に任されており、こちらからは変えられない。上と同じ理由で、暗号化した転送の秘密はそこに依存していない。
  - **前方秘匿性**: 設計が要る。受信側が転送のたびに使い捨ての鍵（約 1.2 kB）を見せ、送信側がそれをカメラで読んでから暗号化する形になり、**「送る側が流し始めるだけ」という今の使い方が変わる**（受信側の画面を先に読む手順が増える。QR なら 3〜4 個）。使える場面は Two-way（送信側にカメラがある）か、ネットワーク接続があるときに限られる。やるなら「相手が対応していれば自動で使う、追加の手順が要る場面では選べる」形が候補。ユーザーの判断待ち。
- 2026-10-12: 実機（iPhone のホーム画面アプリ ⇄ Mac の Firefox）で、従来の ID での登録、新しい ID への置き換え（同じ記録に鍵が足される）、耐量子での転送ができた（ユーザーの確認）。
- 2026-10-12: フェーズ 6（ユーザーの判断:「前方秘匿性は、あなたの案で。secure では必須に。256 bit の鍵もできれば。相手が非対応なら格下げして警告」）。
  - **前方秘匿性**（PROTOCOL §9.2）: 受信側が転送の前に使い捨ての鍵（1.2 kB。QR 3〜4 個、または文字列）を見せ、送信側はそれも使って暗号化し、受信側は届いたら消す。
    - 最初の案では「使い捨ての鍵に署名が要る」と考えていた（署名を付けると 4.6 kB、QR 12 個）。**持ち続ける鍵と使い捨ての鍵の両方が無いと開けない** 形にしたので、署名は要らなくなった（すり替えても、すり替えた者には何も開けない）。
    - CLI: `recv --one-time-key` が作って表示（文字列＋端末の QR）、`send --one-time-key <文字列 | camera>` が使う。Web: Receive の「Show a one-time key」、Send の「Scan the receiver's one-time key」/ 貼り付け。
    - `--secure` は前方秘匿性つきの転送だけを送り・受け取る（受信側は最初に鍵を作って表示する）。
    - 鍵を消すのは「保存が終わったとき」。使われなかった鍵・途中で止まった転送の鍵は 1 日で消す。
    - どう守られているかの表示は 3 段階になった: forward secrecy · post-quantum ／ post-quantum ／ older encryption。
  - **直結の鍵を 256 ビットに**（PROTOCOL §12.2）: CLI 同士の TCP 直結。鍵の後半を offer の末尾に足した（古い版はそこまで読まないので、前半だけで接続してくる）。送信側は最初のレコードを 256 ビット → 128 ビットの順に試し、格下げしたら警告する。公開版 0.1.9 との組み合わせで、両方向とも「つながる＋警告が出る」を確かめた。前回「見送り」としたのは、格下げの方法を考えずに「形式を変えると古い版とつながらない」と判断していたため。
  - WebRTC（ブラウザが関わる直結）は従来のまま: 暗号は DTLS で、こちらからは変えられない。offer に載せている 16 バイトは暗号の鍵ではなく「画面を見た」ことの証明に使う値。
- 残っていること: 前方秘匿性と 256 ビット鍵の実機での確認、Two-way やネットワーク接続を使って使い捨ての鍵を自動で渡すこと（いまは受信側が見せて送信側が読む手順が要る）、リリース。
