# QRSend Protocol v1

> ステータス: ドラフト（v0.x 実装と同時に確定させていく）。
> 本書のバイト列はすべて **リトルエンディアン**。「MUST / SHOULD / MAY」は RFC 2119 の意味で用いる。

## 1. 全体像

QRSend の 1 回の送信（**セッション**）は、次の 2 つのオブジェクトから成る。

| オブジェクト | 内容 | セグメント番号 |
|---|---|---|
| **Meta** | manifest（ファイル一覧・ハッシュ等）を封入したもの | 0 |
| **Body** | ファイル内容を連結したペイロードを圧縮（・暗号化）したもの | 1 ..= N |

Body は固定長（`2^seg_shift` バイト、最後のみ短い）の **セグメント** に分割され、Meta は単独で 1 セグメントとなる。
各セグメントは独立に **RaptorQ（RFC 6330）** で符号化され、得られた符号化シンボルが 1 枚ずつ **フレーム** に格納される。
フレームは **Base45** で文字列化され、**QR コード（英数字モード）** として表示される。

```
payload ─ zstd ─ [age] ─▶ Body ─ split ─▶ seg 1..N ─┐
manifest ─ zstd ─ envelope ─ [age] ─▶ Meta = seg 0 ─┴─ RaptorQ ─▶ symbols ─▶ frames ─ Base45 ─▶ QR
```

受信側は、どのフレームをどの順で受け取ってもよい。各セグメントについて、ソースシンボル数 `K` よりわずかに多い数のシンボルを集めれば、そのセグメントを復元できる。

## 2. QR 層

- QR の内容は、フレームのバイト列を **Base45（RFC 9285）** でエンコードした文字列とする。
  - Base45 の文字集合は QR 英数字モードの文字集合と完全に一致するため、英数字モードで格納できる（バイトモードの約 97% の効率）。
  - BarcodeDetector API のように読み取り結果を文字列でしか返さないデコーダでも、内容が壊れない。
- シンボルサイズ `T` は、選んだ QR バージョン・誤り訂正レベルで格納できる最大バイト数から決まる。送信側は 1 回の送信の間 `T` を固定する SHOULD。再送（resume）時など送信の実行ごとに `T` が変わることは許され、受信側は同じ `T` のシンボルだけを 1 つのセグメントのデコードに用いる MUST（`T` は CRC 後のフレーム長から決まる）。

- 送信側は任意のマスクパターンを使ってよい。参考実装は生成速度のため常にマスク 0 を使う（最適マスクの選定はコード生成時間の大半を占め、QRSend のペイロードは圧縮・暗号化済みで偏りが無いため効果も無い）。

### 2.1 密度プリセット（参考実装の既定値）

| 名前 | QR バージョン | 誤り訂正 | 用途 |
|---|---|---|---|
| `low` | 15 | M | 小さな画面・古いカメラ |
| `normal` | 25 | L | 既定 |
| `high` | 32 | L | PC の大画面・録画モード |
| `max` | 40 | L | 録画モードの限界 |

参考実装の既定（`auto`）は転送量で決める: Meta と Body を合わせて 4 シンボル以内に収まる最小のもの（v10-M → v15-M → v20-M の順に試す）、収まらなければ `normal`。

### 2.2 複数コードの同時表示（グリッド）

送信側は 1 画面に複数のコードを並べてよい。受信側が格子を手がかりに読めるよう、参考実装は次の配置を使う。

- 同じバージョンのコードを `cols × rows` の格子に並べる（正方形である必要はない）。
- 隣り合うコードの間隔と、格子の外周の余白は **4 モジュール**（クワイエットゾーン 1 つ分を隣と共有する）。したがってコードのピッチは `(modules + 4)` モジュールである。
- 受信側は、どれか 1 つのコードを検出したら、その四隅から格子の周期を求め、隣のセルを切り出して個別にデコードしていくことができる（参考実装の CLI はこの方法で、1 フレームに数百個のコードを読む）。この配置に従わない送信側のフレームも、通常の検出で読める範囲では受理される。

### 2.3 カラーコード（任意）

1 つの枠に **3 個の独立した QR コード** を重ねて表示してよい（MAY）。3 個はそれぞれ画像の赤・緑・青の成分に載せる。あるコードの暗モジュールは、その成分を 0 に、明モジュールは最大にする（白地。3 個とも暗なら黒、赤のコードだけ暗ならシアンになる）。3 個は同じバージョン・同じ位置とし、内容は互いに無関係な別々のフレームである。

- 受信側は、画像を成分ごとの濃淡画像に分けて、それぞれを通常の QR として読む。フレームは噴水符号のシンボルなので、読めた成分の分だけ受信が進み、読めなかった成分は単なる欠落になる（誤ったデータにはならない）。
- カラーであることを知らせる信号は無い。受信側は、3 成分から読めたコードが互いに異なるかどうかで判別する SHOULD（白黒の表示なら 3 成分とも同じコードになる）。濃淡画像として読んでも緑のコードは読めることが多いので、判別前でも転送は進む。
- カメラ経由では、表示とセンサーの色の重なり、ホワイトバランス、色差の間引き（4:2:0）のため、白黒より大きいモジュールが必要になる。画面キャプチャのように画素がそのまま届く経路で最も効果がある。

## 3. フレーム形式

| オフセット | サイズ | フィールド | 説明 |
|---|---|---|---|
| 0 | 2 | `magic` | `0x51 0x53`（"QS"） |
| 2 | 1 | `version` | `0x01` |
| 3 | 1 | `flags` | bit0: `ENCRYPTED`。bit1–7 は予約（送信側は 0 にする MUST。受信側は未知のビットが立ったフレームを破棄する MUST） |
| 4 | 4 | `session_id` | u32。セッションごとのランダム値 |
| 8 | 1 | `seg_shift` | Body セグメントの公称サイズ（`2^seg_shift` バイト）。12 ≤ `seg_shift` ≤ 30 |
| 9 | 3 | `seg_count` | u24。Body セグメント数 N（0 可） |
| 12 | 3 | `seg_index` | u24。0 = Meta、1..=N = Body |
| 15 | 4 | `seg_len` | u32。このセグメントのバイト長（≥ 1） |
| 19 | 3 | `esi` | u24。RaptorQ の Encoding Symbol ID |
| 22 | T | `symbol` | 符号化シンボル。T ≥ 16 |
| 22+T | 4 | `crc32` | オフセット 0 から 22+T までの CRC-32（IEEE 802.3） |

ヘッダ 22 バイト ＋ CRC 4 バイト = 1 フレームあたり 26 バイトのオーバーヘッドとなる。

### 3.1 受信側の検証規則

受信側は、以下のいずれかに当たるフレームを **破棄する MUST**。

- CRC が一致しない
- `magic` / `version` が未知
- `seg_index > seg_count`
- Body セグメントで `seg_len > 2^seg_shift`
- Body セグメント i（< N）で `seg_len ≠ 2^seg_shift`
- `ceil(seg_len / T) > 56403`（RaptorQ の 1 ブロックあたり最大ソースシンボル数）
- 同一セッション内で `flags`・`seg_shift`・`seg_count`・同一セグメントの `seg_len` が以前のフレームと食い違う

シンボルサイズ `T` はフレームごとに違ってよい（QR の密度を変えて送り直した場合や、複数の経路を同時に使う場合。§13）。ただし 1 つのセグメントは 1 つの `T` のシンボルだけから復元するので、受信側は §13 の規則でどの `T` で集めるかを決める。

受信側は、最初に受理したフレームの `session_id` にロックする SHOULD。異なる `session_id` のフレームは無視し、利用者に通知する。

## 4. 前方誤り訂正（RaptorQ）

- 各セグメントは、RaptorQ の **単一ソースブロック**（`Z = 1`、`N = 1`、`Al = 1`）として符号化する。OTI は `transfer_length = seg_len`、`symbol_size = T` とする。
- セグメントは末尾を 0 で埋めて `K = ceil(seg_len / T)` 個のソースシンボルにする。復元後は `seg_len` バイトに切り詰める。
- ESI は RFC 6330 に従う。`esi < K` はソースシンボル（systematic）、`esi ≥ K` は修復シンボルである（内部シンボル番号は ISI = ESI + K' − K、K' は拡張ソースシンボル数）。

### 4.1 送信スケジュール（参考実装・規範ではない）

受信側はスケジュールに依存してはならない（MUST NOT）。参考実装は次のように送信する。

- **パス**: 0 から始まる番号。パス p では、各セグメントについて「シンボル番号」`j ∈ [p·(K+R), (p+1)·(K+R))` を送る。ESI = `j mod 2^24` とする（`j < K` はソースシンボル、それ以外は修復シンボル）。`R = ceil(K · redundancy) + 2`（既定 `redundancy = 0.10`）。
- **インターリーブ**: 連続する W 個（既定 8）のセグメントを 1 つの窓とし、窓内でシンボルを 1 つずつ巡回させる。カメラの一時的な乱れが 1 つのセグメントに集中するのを防ぐためである。
- **Meta の優先**: Meta は各パスの先頭の窓に通常のセグメントとして含める。加えて、Meta のシンボルを 10 フレームに 1 回（既定値）差し込む。差し込む分のシンボル番号は `2^23` から始まる独立したカウンタで進め、通常の巡回と ESI が重複しないようにする。
- 全窓を巡回し終えたら次のパスへ進む。シンボルは無限に生成でき、利用者が止めるまで送信を続ける。
- **フィードバックがあるとき**（§11）: 受信側が「受信済み」と報告したセグメント（Meta を含む）は送らない。現在の窓に未受信のセグメントが残っている間は次の窓へ進まず、そのセグメントの新しいシンボルを送り続ける（1 回の延長は 1 パス分の 1/10、最大 40 回）。これにより、損失が冗長度を超えていてもセグメントは「次のパス」を待たずに完成し、損失が無ければ冗長分を送らずに済む。フィードバックが途絶えたら 2 段階で元に戻す（参考実装の値）: 2 秒読めなければ「窓の完成を待つ」のをやめ（最後の報告で受信済みとされたセグメントは引き続き省く）、10 秒読めなければ受信状況は不明とみなして全セグメントの送信に戻る。再び読めたら、その内容に従う。

## 5. Meta

### 5.1 エンベロープ

Meta セグメントの平文は次の形式とする。

| サイズ | フィールド | 説明 |
|---|---|---|
| 3 | `magic` | `"QSM"` |
| 1 | `version` | `0x01` |
| 1 | `sig_alg` | 0 = 署名なし、1 = Ed25519 |
| 32 | `signer` | `sig_alg = 1` のとき: 送信者の Ed25519 公開鍵 |
| 64 | `signature` | `sig_alg = 1` のとき: `"QRSEND-META-v1" ‖ session_id(4) ‖ manifest_z` への署名 |
| 残り | `manifest_z` | zstd で圧縮した manifest JSON（UTF-8） |

`ENCRYPTED` フラグが立っている場合、Meta セグメントのバイト列は上記平文を **age（X25519 受信者）** で暗号化したものとなる。

### 5.2 manifest JSON

```json
{
  "qrsend": 1,
  "session": "1a2b3c4d",
  "kind": "files",
  "created": 1790000000,
  "sender_name": "chimo-macbook",
  "body": {
    "length": 1048576,
    "blake3": "<hex>",
    "segment_blake3": ["<hex>", "..."],
    "encoding": "zstd",
    "plain_length": 4194304
  },
  "entries": [
    { "path": "photos", "type": "dir" },
    { "path": "photos/a.jpg", "type": "file", "size": 2048, "blake3": "<hex>", "mode": 420, "mtime": 1789990000 }
  ]
}
```

| フィールド | 説明 |
|---|---|
| `qrsend` | manifest のバージョン（1） |
| `session` | `session_id` の 16 進表記（8 桁、ビッグエンディアン表記）。フレームヘッダと一致しなければならない MUST |
| `kind` | `"files"`（ファイル・フォルダ）または `"text"`（テキスト） |
| `created` | UNIX 秒 |
| `sender_name` | 任意。表示用の名前（検証済みとは限らない） |
| `body.length` | 送信される Body のバイト長 |
| `body.blake3` | 送信される Body 全体の BLAKE3 |
| `body.segment_blake3` | Body セグメントごとの BLAKE3（送信されるバイト列に対して計算） |
| `body.encoding` | `"zstd"` または `"none"`。暗号化前の段階での符号化方式 |
| `body.plain_length` | 復号・展開後のペイロード長 |
| `entries[]` | `kind = "files"` のときのエントリ一覧（並び順に意味がある） |
| `entries[].path` | `/` 区切りの相対パス（UTF-8） |
| `entries[].type` | `"file"` または `"dir"`。シンボリックリンクは送信しない |
| `entries[].size` / `blake3` | ファイルのバイト長と BLAKE3（平文に対して計算） |
| `entries[].mode` | 任意。UNIX パーミッション。受信側は実行ビットのみを尊重する SHOULD |
| `entries[].mtime` | 任意。UNIX 秒 |

未知のフィールドは無視する MUST。

## 6. Body

- **ペイロード**:
  - `kind = "files"`: `entries` のうち `type = "file"` のものの内容を、並び順どおりに **単純連結** したもの。区切りやヘッダは入れない（境界は `size` から決まる）。
  - `kind = "text"`: UTF-8 テキストそのもの。
- **符号化**: `encoding = "zstd"` ならペイロード全体を zstd で圧縮する。圧縮結果は **1 つ以上の zstd フレームの連結** とする（受信側は連結されたフレームを順に展開する MUST）。メモリを一定に保つため、実装は入力を一定サイズごとに別フレームとして圧縮してよい。
- **暗号化**: `ENCRYPTED` のとき、圧縮後のバイト列を age で暗号化する。age の STREAM 構造により、暗号文は単体で正規の `.age` ファイルとなる。
- **分割**: 得られたバイト列を `2^seg_shift` バイトごとに区切って Body セグメント 1..=N とする。

### 6.1 受信側の展開規則

- 各 Body セグメントの BLAKE3 を `segment_blake3` と照合し、一致しないセグメントは破棄して受信し直す MUST。Meta の到着前に完成したセグメントは、検証保留として保持してよい。
- 展開時には、各エントリのパスを §7 に従って無害化する MUST。
- 展開されたバイト数が `plain_length` を超えた時点で中止する MUST（圧縮爆弾対策）。
- 各ファイルの BLAKE3 を照合し、不一致なら失敗として扱う MUST。

## 7. パスの無害化

受信側は各 `path` を次の規則で検査・変換する。

- 空、絶対パス（`/` や `\` で始まる、ドライブレター付き）、`..` や `.` のコンポーネント、NUL を含むものは **拒否** する。
- `\` はパス区切りとしては扱わず、§7 の置換対象とする。
- 各コンポーネント中の `< > : " | ? * \` および制御文字は `_` に置換する。
- 末尾のドットと空白は除去する。
- Windows の予約名（`CON`, `PRN`, `AUX`, `NUL`, `COM1–9`, `LPT1–9`。拡張子付きを含む）には先頭に `_` を付ける。
- 1 コンポーネントは 255 バイト以下とする。超える場合は拒否する。
- 無害化の結果、パスが重複したエントリは拒否する。

## 8. Resume code

受信側は、欠けているセグメントの一覧を **resume code** として提示できる。送信側はこれを受け取り、該当セグメントだけを送り直す。

```
QSR1-<BASE32>
```

BASE32 は RFC 4648 のアルファベット（パディングなし、大文字）とし、次の内容を表す。

| フィールド | 説明 |
|---|---|
| `session_id` | u32 |
| `range_count` | LEB128 |
| 範囲 × `range_count` | `(start_delta: LEB128, run_len: LEB128)`。`start_delta` は直前の範囲の終端からの差分。セグメント番号には Meta（0）も含む |
| `check` | 上記全体の CRC-32 の下位 16 ビット（u16） |

送信側は `session_id` に対応するスプール（送信データのキャッシュ）を保持している場合に限り、resume code を受け付ける。

## 9. 暗号化と署名

- 各デバイスは **X25519**（age の identity / recipient）と **Ed25519**（署名）の鍵ペアを持つ。
- **フィンガープリント**: `BLAKE3("QRSEND-FPR-v1" ‖ age_recipient(ASCII の age1… 文字列) ‖ ed25519_pk(32))` の先頭 8 バイトを u64（LE）として 10^12 で割った余りを、10 進 12 桁を 4 桁ずつ区切って表記したもの（`4829-1306-5512` 形式、約 40 ビット）。ペアリング時の目視確認に用いる。6 桁程度では攻撃者が一致する鍵を総当たりで作れてしまうため、12 桁とした。
- **デバイス ID の共有形式**: `qrsend-id:1:<x25519 age recipient>:<ed25519 公開鍵の base64url（パディングなし）>:<name の percent-encoding>`。QR 1 枚（通常のモード自動選択・誤り訂正 M）で表示する。
- **秘密鍵ファイル**（参考実装）: `name=` / `x25519=AGE-SECRET-KEY-1…` / `ed25519=<seed の base64url>` の行からなるテキスト。権限 0600 で保存する。
- **平文送信**: 送信者は受信者を指定しない平文送信を、利用者が明示的に選んだ場合にのみ行う SHOULD（参考実装では `--plain`）。平文送信でも、送信者が ID を持っていれば署名を付ける。
- `ENCRYPTED` セッションでは、Meta と Body をそれぞれ **独立した age ファイル** として、同じ受信者集合に宛てて暗号化する。
- 署名は Meta エンベロープ（§5.1）に入れる。受信側は、署名者が Trusted devices に含まれていれば `From: <name> ✓`、含まれていなければ `Unverified sender` と表示する MUST。署名が付いていて検証に失敗した場合は、そのセッションを拒否する MUST。manifest の `sender_name` は自己申告であり、署名の検証結果とは別に扱う。
- Body は、署名済み manifest 内の `body.blake3` と `segment_blake3` によって間接的に認証される。

## 10. バージョニング

- フレーム形式の非互換な変更は `version` を上げて行う。
- manifest への後方互換なフィールド追加は `qrsend` 番号を変えずに行える（受信側は未知のフィールドを無視するため）。
- フィードバック（§11）への後方互換なフィールド追加は、範囲リストの後ろに追記して行う（送信側は未知の末尾を無視する）。

## 11. フィードバック（受信側 → 送信側）

受信側は、受信状況を **フィードバックコード** として送信側に伝えられる（MAY）。送信側はそれを読めるとき（カメラが受信側の画面を見ているなど）に限り利用する。フィードバックが無くても転送は成立しなければならない（MUST）。逆方向の伝送路は規定しない。参考実装は、受信側の画面に QR コード 1 個として表示し、送信側のカメラで読む。

### 11.1 送信側からの合図（notice）

フィードバックを読める送信側は、その旨を **notice** として知らせる。notice はフレームではない独立したコードで、データのコードに混ぜて流す。notice を知らない受信側はフレームでないコードとして無視するので、互換性は保たれる。

```
QSC1-<BASE45>
```

| フィールド | 説明 |
|---|---|
| `session_id` | u32（リトルエンディアン） |
| `caps` | u8。bit0 `WANTS_FEEDBACK`（送信側はフィードバックコードを読める）、bit1 `HEARS_SOUND`（送信側はマイクで聞いている。フィードバックを音で返してよい。§14）。他のビットは予約（受信側は無視する） |
| （将来の拡張） | 受信側は読み飛ばす |
| `check` | 上記全体の CRC-32 の下位 16 ビット（u16） |

- 受信側は、ロックしているセッションと同じ `session_id` の notice で `WANTS_FEEDBACK` が立っているのを見たときに限り、フィードバックコードを表示する SHOULD（頼まれていないのに表示しない）。`WANTS_FEEDBACK` が下りた notice を見たら表示をやめてよい。
- 受信側は、全部受け取り終えた後もしばらく（参考実装は 8 秒）notice を待つ SHOULD。短い転送は最初の notice が届く前に終わることがあり、その場合でも送信側に「全部届いた」と伝えるためである。
- 送信側は notice を挟む頻度を自由に決めてよい。参考実装は、フィードバックがまだ読めていない間は 8 コードに 1 回（最初の 240 コード。以後は 32 コードに 1 回）、読めている間は 64 コードに 1 回とする。

### 11.2 フィードバックコード

```
QSF1-<BASE45>
```

BASE45 は RFC 9285（フレームと同じ。QR の英数字モードに収まる）で、次の内容を表す。

| フィールド | 説明 |
|---|---|
| `session_id` | u32（リトルエンディアン） |
| `state` | u8。bit0 `COMPLETE`（全セグメントを受信・検証・保存し終えた）、bit1 `TRUNCATED`（範囲リストを途中で打ち切った） |
| `seq` | LEB128。受信側が 1 回の実行の中でフィードバックを作るたびに増える番号 |
| `frames` | LEB128。このセッションのフレームを重複を除いて何個読めたか（累計）。送信側は自分が表示した数と比べて損失率を見積もれる |
| `remaining` | LEB128。完了までに必要なシンボル数の見積もり（現在のシンボルサイズ換算の下限値） |
| `range_count` | LEB128 |
| 範囲 × `range_count` | まだ受信していないセグメント。符号化は resume code（§8）と同じ `(start_delta, run_len)`。Meta（0）も含む |
| `symbol_size` | LEB128。`remaining` を数えた単位（シンボルサイズ、バイト）。経路によってシンボルサイズが違うので、送信側は `remaining × symbol_size` でおよその残りバイト数を得る。無い場合（0 を含む）は不明 |
| `reads` | LEB128、任意（0.1.3 の次の版から）。受信側のカメラが 1 秒に何枚読めているか（10 倍した整数）。`dot` と組で付ける。どちらも 0、または無い場合は不明 |
| `dot` | LEB128、任意。コードの 1 ドット（モジュール）がカメラの何ピクセルに写っているか（10 倍した整数）。受信側は、検出したコードの大きさと文字数から見積もる |
| （将来の拡張） | 送信側は読み飛ばす |
| `check` | 上記全体の CRC-32 の下位 16 ビット（u16） |

- 範囲は最大 24 個とする。それより多いときは先頭の 24 個だけを載せて `TRUNCATED` を立てる。送信側は、最後の範囲より後ろのセグメントを「すべて未受信」とみなす（MUST。送り過ぎる方向に倒す）。
- `COMPLETE` は、受信側が全体の BLAKE3 とファイルの BLAKE3 まで検証し終えてから立てる（MUST）。セグメントがそろっただけの段階では、範囲リストを空にして `COMPLETE` は立てない。
- 送信側は `session_id` が一致しないフィードバックを無視する（MUST）。
- フィードバックは **認証されていない助言** である。送信側はこれを「送る量を減らす」「送り方を調節する」「利用者に完了を知らせる」ためだけに使い、到達の証明として扱ってはならない（MUST NOT）。偽のフィードバックで起こせるのは送信の早期終了（やり直せば済む）までである。
- 受信側は、検証に失敗して捨てたセグメントを再び未受信として報告する。送信側は、いったん受信済みとされたセグメントが未受信に戻ることを受け入れる（MUST）。
- 受信側は、同じコードを少なくとも 0.3 秒程度は表示し続ける SHOULD（カメラが確実に 1 回読めるようにするため）。

### 11.3 途中で途切れたとき

逆方向の伝送路は、いつ途切れてもおかしくない（手で遮られる、端末がずれる、受信側のページが閉じる）。次の性質を保つこと。

- **順方向は逆方向に依存しない**。フィードバックが一度も届かなくても、途中から届かなくなっても、送信側は送り続け、受信側は従来どおり完了できる（MUST）。送信側は「フィードバックが来るまで待つ」動作をしてはならない（MUST NOT）。
- **古い情報を信じ続けない**。送信側は、最後に読めたフィードバックの内容を無期限に使ってはならない（MUST NOT）。一定時間読めなければ「受信側は何も持っていない」とみなして全セグメントの送信に戻る（§4.1 の 2 段階）。受信側が途中で状態を失っていても（保存できない環境での再読み込みなど）、これで必ず回復する。
- **受信済みの取り消しを受け入れる**。再び読めたフィードバックが、以前「受信済み」だったセグメントを未受信としていたら、それを送り直す（MUST）。
- **待ちすぎない**。受信側が特定のセグメントをいつまでも完成できない場合に備え、送信側が 1 つの窓にとどまる回数には上限を設ける SHOULD（参考実装は延長 40 回）。
- **順方向だけが途切れた場合**（受信側のカメラが送信側の画面を見失った）は、フィードバックの内容が変わらなくなるだけで、特別な扱いは要らない。再び見えれば続きから進む。
- **受信側は 1 台を想定する**。フィードバックを使うと、送信側はその 1 台がすでに持っている分を送らなくなる。同じ画面を複数の受信側に同時に見せる使い方では、フィードバックを使わないこと。
- 受信側での保存（Inbox）と resume code（§8）は従来どおり働く。フィードバックが途切れたまま送信が止まっても、後から続きを受け取れる。

### 11.4 フィードバックを使った表示の自動調節（参考実装・規範ではない）

フィードバックの `frames`（受信側が読んだ、重複を除いたコードの数）の増え方を見れば、送信側は「いまの表示がどれだけ読めているか」を知ることができる。参考実装（`qrsend_core::tune::Tuner`、Web の preview「Automatic speed」）はこれを使って、**1 秒あたりの枚数** と **1 枚あたりのコード数**（画面に収まる配置を、少ない順に並べたものの中から選ぶ。正方形とは限らない）を自動で決める。

- 1 つ変えて試す → 1 秒待つ（古い設定の分が残っているため）→ 2.5 秒測る → 受信側が 1 秒あたりに読んだコード数が 5% 以上増えていれば採用、そうでなければ元に戻す。
- 試す向きは、表示したコードのうち読まれた割合で決める: 半分以上読めていれば「速く」「密に」、半分未満なら「遅く」「疎に」。逆向きは試さない（損をするだけで得が無い）。何も読めていないときは、良くならなくても「遅く」「疎に」を続ける。
- 効果が無かった向きは 3 回ぶん休ませ、失敗が続くたびに休みを倍にする（最大 24 回）。条件が変わったとき（距離、明るさ、手ぶれ）に備えて、やめてしまうことはしない。
- フィードバックが 1.5 秒途切れたら、測りかけの結果は捨てる。ネットワーク接続（§12.1）が張れている間は調節しない（`frames` に接続経由の分が混ざるため）。
- **最初の一手はカメラの申告で決める**: フィードバックに `reads` と `dot`（§11.2）が付いていて、まだ何も変えていなければ、送信側は一気に設定を決める。枚数は `reads` の 0.9 倍、配置は「いまの `dot` × その配置での画面上のドットの大きさ ÷ いまの配置でのそれ」が 4 ピクセル以上になる最も密なもの（いまより疎にも遅くもしない）。申告を使うのはこの 1 回だけで（以後の値は、試している最中の設定のものかもしれない）、そこから先は上の山登りで詰める。
- 実測（同じ Mac の 2 つのページを仮想カメラでつないだ e2e）: 1 個・10 枚/秒（4.9 KiB/s）から始めて、山登りだけでは 20 秒で 4×2・22 枚/秒（約 54 KiB/s）に落ち着いた。カメラの申告を使うと、最初のフィードバックの時点で 4×2・27 枚/秒になり、最初の 2 秒から約 47 KiB/s が出る。

## 12. リンクコード（別の経路の確立）

2 台が別の経路（今のところローカルネットワークの直接接続）を張るための小さなメッセージを、コードとしてやり取りする。フレームではないので、知らない実装は無視する。

```
QSL1-<BASE45>
```

| フィールド | 説明 |
|---|---|
| `session_id` | u32（リトルエンディアン） |
| `kind` | u8。1 = offer（送信側から）、2 = answer（受信側から） |
| `id` | u8。同じ種類のメッセージを区別する番号。answer は対応する offer の `id` を返す |
| `part` / `parts` | u8 / u8。長いメッセージを分割したときの番号（0 始まり）と総数 |
| `payload` | 中身（経路ごとに定義。下記） |
| `check` | 上記全体の CRC-32 の下位 16 ビット（u16） |

- 送信側は offer を、ストリームのコード 1 個に収まる長さに分割してデータの合間に繰り返し流す（参考実装は 6 コードに 1 回、notice と交互）。受信側は全部の `part` がそろったら 1 つのメッセージとして扱う。
- 受信側は offer を受けたら answer を返してよい（MAY）。利用者に確認するかどうかは実装が決める。参考実装は確認せずに応じ（offer は目の前の送信側の画面からしか届かず、接続先もローカルネットワークに限られるため）、利用者がいつでも切れるようにしている（切ったらその転送では再接続しない）。answer は受信側の画面に QR コード 1 個として表示し、送信側のカメラで読む。

### 12.1 ローカルネットワーク（WebRTC データチャネル）

`payload` は接続に必要な最小限の情報である: `ufrag`、`pwd`（それぞれ長さ 1 バイト＋ ASCII）、DTLS 証明書の SHA-256 フィンガープリント（32 バイト）、候補数（1 バイト）、候補 ×（アドレスの長さ 1 バイト＋文字列、ポート u16 ビッグエンディアン）。候補はホスト候補（UDP）だけを最大 4 個載せる。STUN / TURN は使わず、ローカルネットワークの外には接続しない。受け取った側はこれから SDP を組み立てる（offer 側が `actpass`、answer 側が `active`）。

- 接続は DTLS で暗号化され、その証明書のフィンガープリントはコード（＝互いの画面）を通じて交換される。QRSend 自身の暗号化・署名（§9）はその上でそのまま働く。
- **チャネル上のやり取り**:
  - 受信側 → 送信側はテキストのメッセージで、改行区切りの行からなる: `B1`（バイナリのメッセージを受け取れる。接続直後に 1 回送る）、`A<n>`（この接続で受け取ったレコードのうち n 個を取り込み終えた。接続ごとに 0 から数える）、フィードバックコード（§11.2）。
  - 送信側 → 受信側は、相手が `B1` を送ってきたら **バイナリのメッセージ** で送る SHOULD: レコードを並べたもので、各レコードは「長さ（u32、リトルエンディアン）＋中身」。中身はフレームのバイト列（§3。Base45 にしない）か、それ以外のコード（notice など）の文字列（UTF-8）で、先頭 3 バイト目がフレームの版数（`0x01`）かどうかで見分ける。`B1` を送ってこない受信側（0.1.2）には、コードの文字列を改行で区切ったテキストのメッセージで送る。どちらも 1 メッセージは 256 KiB 未満。
  - 受信側は、変化が無くても 1 秒に 1 回はフィードバックを送り直す SHOULD（大きな転送は展開に時間がかかる。黙っていると送信側が「受信側を見失った」と判断する）。
- 受信側は返信を **0.1 秒に 1 通程度にまとめる** SHOULD。受け取ったメッセージごとに小さな返信を返すと、ブラウザのデータチャネルは極端に遅くなる（実測で 15 MB/s が 0.6 MB/s に落ちた）。
- 送信側は、`A<n>` を使って送る速さを決める SHOULD。参考実装（`LanSender`）は **ペース（1 秒あたりのレコード数）** を動的に決め、その速さでブラウザに渡す: 2 MiB/s から始め、確認が返るたびに、受信側が追いついていれば（未確認分がペースの 0.15 秒ぶん未満）1.5 倍にする。ただし 1 回の上げ幅は 4 MiB/s まで。未確認分が 0.3 秒ぶんを超えたら「実際に届いた速さ」の 0.9 倍まで下げ、以後はその手前（下げる前の 0.7 倍）までは速く、そこから先は 3% ずつ上げる。1.5 秒確認が無ければ 4 分の 1 にする。8 秒確認が無ければその接続は使えないものとして閉じ、offer をやり直す。
  - 「未確認分の上限」だけで制御すると、渡した分をブラウザが一気に送り、SCTP 自身の輻輳制御が倍々に増やした末にパケットを落として 1〜3 秒止まる（同じ Mac 内の実測で、転送のたびに 1 MiB 前後の地点で発生。最初から全部流し込んだ場合は 359 パケットが捨てられ 8 秒止まった）。ペースを付けて渡すと「直前に通った量＋少し」しか頼まないので落ちない。上げ幅の上限が無いと高速域で同じことが起きる（0.5 秒で 23 → 115 MiB/s に上がって再び落とした）。
  - 実測（同じ Mac の 2 つの Chrome、展開まで含む）: 100 MB が 19.9 MiB/s（ばらつき 12.7〜23）→ 28.5 MiB/s（安定。定常時のペースは約 70 MiB/s）。
- このチャネルで流すフレームは、QR には収まらない大きなシンボル（参考実装は 4096 バイト）でよい。1 MiB のセグメントが 256 シンボルになる。
- **失われない経路では噴水符号を使わない**（参考実装、`DirectSender`）: データチャネルは順序どおり・欠落なしで届くので、各セグメントの **ソースシンボル（ESI < K）を先頭から 1 回ずつ** 送るだけにする。送信側は切り出すだけ、受信側は並べるだけで、どちらにも符号の計算が生じない。フレームの形式は同じなので、受信側は何も知らなくてよい。
  - 例外は「別のシンボルサイズで集め始めていたセグメント」（接続前に画面から読んでいた分。§13 の規則で最初の何個かが見送られる）と、検証に失敗して捨てられたセグメント。送信側は全部を 1 回送り終えたら何も送らずにフィードバックを待ち、**受信側が「送った分をすべて取り込んだ」（`A<n>` が送信済みの数に達した）うえでなお欠けていると言うセグメント** にだけ、修復シンボルを K/4 個ずつ追加する。受信側が一度「持っている」と言ったセグメントを再び欠けていると言ったら、そのセグメントは先頭から送り直す。
  - フィードバックが 3 秒届かないまま送るものが無い状態が続いたら、同じ追加を見込みで行う。接続が張り直されたら、その時点のフィードバックを起点に最初からやり直す（前の接続で送った分が届いたとは限らない）。
  - 実測（同じ Mac の 2 つの Chrome、100 MB）: 従来の方式（テキスト、噴水符号のスケジュール）は必要数の 1.44 倍のコードを送っていた（フィードバックが届くまでの間に冗長分と「窓の延長」を送ってしまうため）。新方式は必要数ちょうどで、回線に流れるバイト数は 218 MB → 101 MB。

### 12.2 ローカルネットワーク（TCP、CLI 同士）

ブラウザは TCP の接続を受けることも張ることもできないが、CLI はできる。TCP なら **受信側から接続しに行ける** ので、answer を返す必要が無い（送信側にカメラが要らない）。`kind` = 3（TCP offer）を使う。知らない実装（ブラウザ版を含む）は無視する。

`payload`: ポート（u16、ビッグエンディアン）、鍵（16 バイトの乱数）、アドレス数（1 バイト）、アドレス ×（長さ 1 バイト＋文字列。IPv4 または IPv6 の表記）。参考実装は最大 4 個のアドレスを載せる。

1. 受信側は offer のアドレスに順に接続を試み（参考実装は 1 つあたり 1.5 秒まで）、つながったら `"QSTCP1\n"`（7 バイト）、`session_id`（u32、リトルエンディアン）、乱数 16 バイト（`salt_r`）を送る。
2. 送信側は `session_id` を確かめ、乱数 16 バイト（`salt_s`）を返す。
3. 以後は双方向とも **レコード** の列: 長さ（u32、リトルエンディアン）＋ ChaCha20-Poly1305 の暗号文（認証タグ 16 バイトを含む）。鍵は方向ごとに別で、BLAKE3 の鍵導出（`derive_key`）で `鍵 ‖ salt_r ‖ salt_s` から作る。文脈文字列は送信側 → 受信側が `qrsend 0.1.3 tcp: sender to receiver`、逆向きが `qrsend 0.1.3 tcp: receiver to sender`。ノンスは方向ごとに 0 から数えるカウンタ（u64 リトルエンディアン＋ 0 を 4 バイト）。追加認証データは無い。
4. 受信側の最初のレコードは `B1`。送信側はこれを復号できるまで何も送らない（鍵を知らない相手にはデータが流れない）。
5. レコードの中身は §12.1 のチャネルと同じ: 送信側 → 受信側は「長さ＋中身」を並べたバイナリのメッセージ（フレームは Base45 にしない）、受信側 → 送信側は `A<n>` とフィードバックコードの行。送り方も同じ（ソースシンボルを 1 回ずつ、欠けていると確定した分にだけ修復シンボル）。流量は TCP に任せ、ペースの制御はしない。
6. 受信側は全セグメントを検証して保存し終えたら `COMPLETE` のフィードバックを送り、送信側はそれを受けて終了する。

- **安全性**: 鍵は画面のコードでしか伝わらないので、接続してきた相手が正しいレコードを送れること自体が「送信側の画面を見た」証明になり、同じネットワークの第三者は読むことも書き換えることもできない。接続ごとに両側の乱数を混ぜるので、同じ offer で張り直しても鍵とノンスの組は再利用されない。カウンタのずれ（欠落・並べ替え・再送）は復号の失敗になる。QRSend 自身の暗号化・署名（§9）はその上でそのまま働く。
- 参考実装: `qrsend send --lan`（`--lan-address`、`--lan-port`）、`qrsend recv`（offer を見たら確認なしで接続する。`--no-lan` でしない）。エクスポート（`--export-frames` など）と併用すると、書き出したあとも受信側が全部受け取るまで待ち受ける。
- 実測（同じ Mac、ループバック、非圧縮の 200 MB）: 受信完了まで 1.7 秒（約 114 MiB/s）。その後の検証と書き出しに 1.5〜4 秒かかる（ネットワークとは無関係の既存の処理）。
- macOS では、ファイアウォールが有効だと、署名されていないプログラムへの外からの接続は「受け入れますか」の確認が出るまで（または許可しない限り）切られる。送信側で許可が必要。

## 13. 複数の経路を同時に使う

フレームは噴水符号のシンボルなので、**どの経路から届いたフレームも同じ受信状態に入れてよい**。経路を増やすのに、受信側の仕組みを変える必要は無い。

- **受信側**: 1 つのセグメントは 1 つのシンボルサイズで集める。別のサイズのフレームが届いたら、「そのサイズで届いた分（使わずに見送ったバイト数の累計）」が「いま集めている分（受信シンボル数 × シンボルサイズ）」を上回るまでは見送り、上回ったらそのサイズで集め直す（MUST: 取りこぼしても誤ったデータにはならないこと。SHOULD: この規則）。離れていく経路の残り数個で進捗を捨てることがなく、速い経路が来ればすぐ乗り換える。完成済みのセグメントは影響を受けない。
- **受信側の進捗**（表示とフィードバックの `remaining`）は、最も多くのバイトを運んできたシンボルサイズで数える。
- **送信側**: 経路ごとに別のフレーム列を作ってよい（シンボルサイズも別でよい）。同じ転送を 2 つの経路で送るときは、速い方を先頭のセグメントから、遅い方を末尾のセグメントから進める SHOULD（同じセグメントを二重に送らないため。参考実装では、ネットワーク接続が張れている間、画面のコードは末尾から 1 セグメントずつ送る）。フィードバックはどの経路から届いたものでも、すべてのフレーム列に反映する。
- **どの経路も必須ではない**。経路が増えても減っても転送は続く。画面とカメラの経路は常に動かし続け、他の経路が切れたときの受け皿にする。

## 14. 音（スピーカー → マイク）

短いメッセージを音で運ぶ。遅い（毎秒数十バイト）が、見通しが要らないので、送信側のカメラが受信側の画面を見られない配置（スマホで PC の画面を撮る、普通の姿勢）でもフィードバックを返せる。今のところ用途はフィードバックコード（§11.2）だけで、載せるのは Base45 にする前のバイト列（`check` まで）である。

人のそばで鳴るものなので、聞いて不快でないことを設計の条件にしている: どのデータでも 2 つの音が必ず同じ五音音階（ペンタトニック）に乗るので、不協和にならない。

- **シンボル**: 0.04 秒。低い声部と高い声部が同時に 1 音ずつ鳴らす。各声部は 8 音のうち 1 音（3 ビット）で、1 シンボル 6 ビット。
- **音**（Hz、ハ長調の五音音階）: 低い声部 `523.25, 587.33, 659.26, 783.99, 880.00, 1046.50, 1174.66, 1318.51`（C5〜E6）、高い声部 `1567.98, 1760.00, 2093.00, 2349.32, 2637.02, 3135.96, 3520.00, 4186.01`（G6〜C8）。隣り合う音は 64 Hz 以上離れており、シンボル長の窓の分解能（25 Hz）の 2 倍を超える。
- **鳴らし方**: オルゴールのように、シンボル長の 1/10 で立ち上げ、終わりに向けて約 1/3 まで指数的に減衰させ、最後の 1/10 でなだらかに消す。高い声部は低い声部より小さく鳴らす（参考実装は 0.32 と 0.2）。
- **メッセージ**: プリアンブル 2 シンボル（低・高の音番号が `0, 7`、次が `7, 0`）、続いて `長さ（1 バイト）‖ 中身（0〜255 バイト）‖ 「長さ‖中身」の CRC-32 の下位 16 ビット（LE）` を上位ビットから 3 ビットずつ切り出し、低い声部・高い声部の順に 2 つずつ 1 シンボルにする（余りは 0 で埋める）。フィードバックコード 1 個で約 1.5 秒。
- **受信**: シンボル長の窓で各音の強さ（Goertzel）を測り、グループごとに最も強い音を採る。プリアンブルは 1/4 シンボル刻みで探し、最初に一致した位置から 2 シンボル先までのうち最も強く一致する位置に合わせる（窓が端だけ掛かっていても一致するため）。CRC が合わなければ、そのプリアンブルの直後から探し直す。サンプリング周波数は両側で違ってよい。
- 受信側は、利用者がその転送について明示的に許可した場合に限り音を出す（MUST。許可を覚えておいて次回から黙って鳴らすことはしない）。送信側のマイクは、音声通話向けの加工（エコー除去・雑音抑制・自動音量調節）を切って使う。
